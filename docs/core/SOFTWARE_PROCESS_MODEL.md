# 基于迭代增量模型的 WheatAgent 软件开发过程

## 一、项目概述

### 1.1 项目背景

小麦作为全球三大粮食作物之一，其病害防治直接关系到粮食安全和农业可持续发展。传统小麦病害诊断依赖农业专家人工观察叶片症状进行判断，存在以下突出问题：一是专家资源稀缺且分布不均，偏远地区农户难以获得及时诊断；二是人工诊断主观性强，不同专家对同一症状的判断可能存在差异；三是病害种类繁多（常见小麦病害超过15种），症状相似度高，仅凭肉眼难以精确区分。因此，研发一套自动化、高精度、易部署的小麦病害智能诊断系统，具有重要的理论研究和工程实践价值。

### 1.2 项目目标

本项目旨在构建一个基于多模态特征融合的小麦病害智能诊断系统（WheatAgent），具体目标包括：（1）整合计算机视觉、自然语言处理和知识图谱三种技术路线，实现图像、文本、知识三模态数据的深度融合与利用；（2）构建小麦病害领域知识图谱，实现基于知识增强的诊断推理，提升诊断准确率和可解释性；（3）设计高并发系统架构，支持多用户同时诊断的实时响应需求；（4）通过系统测试与性能评估验证系统的正确性、稳定性和可用性。

### 1.3 项目范围

项目功能范围涵盖：病害图像上传与分析、症状文字输入与语义理解、多模态融合诊断推理、诊断结果展示与知识溯源、诊断记录管理、用户认证与权限控制、知识图谱检索与浏览、系统监控与统计报表。技术范围涵盖：YOLOv8s 目标检测、Qwen3-VL-2B-Instruct 多模态大语言模型推理、Neo4j 知识图谱构建与 GraphRAG 检索增强、KAD-Former 交叉注意力多模态融合、FastAPI+Vue3 前后端分离开发、Docker+Kubernetes 容器化部署。

## 三、各阶段详细实施过程

### 3.1 阶段一：V1 需求分析与技术选型

#### 3.1.1 需求是怎么确定的

2026年2月中旬，项目启动时的第一个问题是：我们需要一个什么样的系统？通过文献调研和用户场景分析，逐步明确了以下核心功能需求：

- **FR-1**：用户可通过 Web 界面上传小麦叶片图像，系统自动检测病害类型和病灶位置
- **FR-2**：用户可输入症状文字描述，系统结合图像和文字进行综合诊断
- **FR-3**：诊断结果应包含病害名称、置信度、防治建议、知识来源追溯
- **FR-4**：系统支持 15 类以上小麦常见病害的识别
- **FR-5**：诊断过程实时推送进度信息，避免长耗时等待
- **FR-6**：支持多用户同时访问和并发诊断
- **FR-7**：具备用户注册、登录、角色权限管理功能

非功能性需求方面，经过对硬件环境（RTX 3050 4GB 显存）的评估，确定了以下指标：单次诊断推理时间不超过 30 秒（GPU 环境）；系统支持至少 3 路并发 GPU 诊断；API 层非 AI 请求响应时间不超过 1 秒；系统代码通过率不低于 95%。

#### 3.1.2 技术选型过程

技术选型这件事，当时有几个关键的考量。最核心的矛盾是：RTX 3050 只有 4GB 显存，而 Qwen3-VL 的 FP16 版本需要约 9.8GB——这是个硬伤。经过调研，发现可以采用 INT4 量化将显存压缩到约 2.6GB，但同时要把 YOLOv8s 和 Qwen3-VL 都塞进同一张卡，还得留一些显存给推理缓存和系统开销。

最终选定的技术栈如下：

| 类别 | 选定技术 | 版本 | 选型理由 |
|------|---------|------|---------|
| 后端框架 | FastAPI | 0.110+ | 原生 async/await 支持，自动 API 文档生成，Pydantic 数据校验 |
| 前端框架 | Vue3 | 3.5+ | Composition API + TypeScript，Vite 极速构建 |
| UI 组件库 | Element Plus | 2.13 | Vue3 生态最佳实践，组件丰富 |
| 视觉检测 | YOLOv8s | ultralytics | FP16 推理高效，15 类病害 mAP@50 达 95.39% |
| 多模态理解 | Qwen3-VL-2B-Instruct | huggingface | INT4 量化后显存 2.6GB，支持 Thinking 推理链 |
| 知识图谱 | Neo4j | 5.x | 原生图数据库，Cypher 查询语言灵活 |
| 关系数据库 | MySQL | 8.0 | 成熟稳定，SQLAlchemy 2.0 异步 ORM 支持 |
| 缓存服务 | Redis | 7.x | 高性能，支持 Token 黑名单和推理缓存 |
| 状态管理 | Pinia | 3.0 | Vue3 官方推荐，TypeScript 完整支持 |
| 测试框架 | Pytest + Playwright | latest | 前后端全覆盖，pytest-asyncio 异步支持 |

> **Git 记录**：此阶段对应项目第一次提交 `1bb77c60`（2026-02-11，frtgi），提交信息为"wheatagentv1.0"。

#### 3.1.3 交付标准

**交付物**：需求规格说明书（含功能需求和非功能需求）、技术方案论证报告（含候选方案对比表）、项目进度计划。

### 3.2 阶段二：V2 系统架构设计

#### 3.2.1 系统是怎么设计的

2月下旬集中做架构设计。核心目标很明确：一个前后端分离的 B/S 架构，前端 Vue3 SPA 通过 HTTP/SSE 与后端通信。

后端的四层分层架构设计是参考了 FastAPI 社区的最佳实践：

```
┌─────────────────────────────────────┐
│  API 路由层 (api/v1/)               │
│  · diagnosis_router  · user_router  │
│  · knowledge_router · health_router │
├─────────────────────────────────────┤
│  Service 服务层 (services/)         │
│  · FusionService (Facade)           │
│  · YOLOService  · QwenService       │
│  · GraphRAGService                  │
├─────────────────────────────────────┤
│  Core 核心层 (core/)                │
│  · security  · config  · database   │
│  · rate_limiter · middleware         │
├─────────────────────────────────────┤
│  Model 数据层 (models/)             │
│  · User  · Diagnosis  · Disease     │
│  · KnowledgeGraph · ImageMetadata   │
└─────────────────────────────────────┘
```

四层之间遵循单向依赖——上层可以引用下层，但下层不能感知上层的存在。这个约束在V3的实际编码中被打破了几次（比如路由层直接调了核心层的数据库连接），但在V4的God File拆分中逐步纠正了。

数据库方面设计了 10 个核心表：users（用户表）、diseases（病害知识库表）、diagnoses（诊断记录主表）、diagnosis_confidences（诊断置信度候选子表）、image_metadata（图像元数据表）、password_reset_tokens（密码重置令牌表）、refresh_tokens（刷新令牌表）、login_attempts（登录审计表）、user_sessions（用户会话表），以及后来加入的 audit_logs（审计日志表，后来在V48中因未被使用而删除）。

融合算法方面，确定了 KAD-Former 作为核心融合算法的设计方向。这个名称来自于三个关键词的组合——Knowledge-Aware（知识感知）、Diffusion（扩散机制）、Former（Transformer架构）。设计了三模态维度适配方案：视觉 768 维→512 维、文本 2560 维→512 维、知识 256 维→512 维。

还有一些关键架构决策是在这个阶段做出的：
- SSE 流式推送方案：设计了 SSEStreamManager 管理六阶段诊断进度推送，asyncio.Queue(maxsize=100) 做背压控制，15 秒心跳 + 120 秒超时保活；
- 三层并发控制方案：SlowAPI 全局限流（令牌桶算法）、DiagnosisRateLimiter GPU 并发限流（最大 3 路，信号量+条件变量）、asyncio.Queue 背压（生产者-消费者模式）。

#### 3.2.2 交付标准

**交付物**：系统架构设计文档（含分层架构图、模块划分表、接口定义）、数据库 ER 图及表结构设计文档、融合算法架构说明文档。

**验收条件**：四层架构设计通过技术评审，数据模型覆盖所有业务需求，接口定义完整且无冗余。

### 3.3 阶段三：V3 核心功能原型验证

#### 3.3.1 这个阶段做了什么

3月上旬是编码密度最高的阶段。目标很明确——把架构设计变成能跑起来的代码。不追求完美，先验证技术可行性再说。

这一轮要实现的功能包括：图像上传与 YOLOv8 视觉检测、症状文字输入与 Qwen3-VL 文本分析、基础多模态诊断结果返回、JWT 用户注册与登录、诊断记录基础 CRUD。

#### 3.3.2 踩过的坑

在V3的具体编码过程中，出现了一个后来被反复提起的问题——"God File"。

最初的想法很简单：把所有诊断相关的逻辑都放在一个文件里，方便调试。于是 `ai_diagnosis.py` 就像滚雪球一样越滚越大，路由、服务调用、SSE 事件生成、验证逻辑全部耦合在一起，最终膨胀到了 **2202 行**。每次想加一个新功能，都得在这个文件里翻上翻下找插入点，改一行代码生怕影响到其他模块。

这个问题在V3的阶段总结中被明确标记为"架构风险"，优先级是最高的 **P0**。但当时为了先保证功能能跑通，决定暂时容忍，放到V4集中解决。

另一个麻烦是认证覆盖不完整。初期只给核心的几个诊断端点加了 JWT 验证，一些管理接口还是裸奔状态。这个问题同样被标记为安全风险，留待后续迭代处理。

#### 3.3.3 原型验证

这一阶段的测试以手动验证为主，没有自动化测试套件。验证方式是端到端走通核心链路：上传一张小麦叶片图像，输入症状描述（如"叶片出现黄色条纹"），看系统能不能返回一个合理的诊断结果。

YOLOv8 的 15 类病害检测基本可用，但存在部分病害类别的检测置信度偏低的问题。Qwen3-VL 的文本分析功能在 INT4 量化之后精度略有下降，但在可接受范围内——这个结论在后面 V5 的精度对比测试中得到了量化验证：纯视觉诊断准确率为 91.7%，加了融合推理之后提升到 96.1%。

> **Git 记录**：V3 原型验证阶段的核心工作最终体现在后续多个提交中。初始代码提交为 `1bb77c60`（2026-02-11），项目评分初始值为 **86.5 分**。

#### 3.3.4 交付标准

**交付物**：可运行的最小可行诊断系统（Web 后端 + 前端），项目评分 **86.5 分**。

**验收条件**：所有核心功能链路可手动走通，系统可在本地环境正常启动并对外提供服务。

**遗留问题**：God File（ai_diagnosis.py 2202行）维护困难（架构风险，P0）、同步代码阻塞事件循环（性能风险，P1）、认证覆盖不完整（安全风险，P1）。

### 3.4 阶段四：V4-V5 架构精化与性能优化

#### 3.4.1 V4：对 God File 动刀

**动机**：V3 遗留的 God File 问题已经到了不改不行的地步。4月4日开始，集中精力做架构重构。这次的策略是——先做拆分让架构合理，再做优化让性能达标。

**实施过程**：实际上这个过程比预想的要复杂得多。把 2202 行的代码拆开不是简单地"剪切粘贴"，关键是要保证拆完之后的功能完全等价。具体做法是：

1. 先把 `ai_diagnosis.py` 中的路由逻辑抽出来，创建 `diagnosis_router.py`；
2. 再把 SSE 相关的事件生成、心跳保活、背压控制全部独立出来，形成 `sse_stream_manager.py`（最终约 450 行）；
3. 参数验证逻辑放到 `diagnosis_validator.py`（约 400 行）；
4. 同时把 `fusion_service.py` 也拆了——从 1268 行拆成 FeatureExtractor（特征提取器）、FusionEngine（融合引擎）、ResultAnnotator（结果标注器）三个子模块，引入 Facade 设计模式统一对外接口。

最惊险的是认证缺失的修复。在拆分过程中发现有两处 API 端点根本没有做 JWT 校验——请求直接就能访问。这个发现让团队出了一身冷汗，立刻作为 P0 安全漏洞修复了。

完成后的效果立竿见影：`ai_diagnosis.py` 从 2202 行缩减到了 **54 行**，减少了 97.5%。项目评分从 86.5 跃升到 **89.8**（+3.3）。

> **Git 记录**：V4 阶段的核心工作对应提交 `5f115124`（2026-04-17，frtgi，提交信息为"4.17change"），以及后续多个 refactor 类型提交。

#### 3.4.2 V5：异步迁移和量化部署

**动机**：V4 解决了架构耦合问题，但新的问题立刻暴露出来了——代码里还有大量同步调用，在异步框架里同步阻塞会导致事件循环卡死，严重影响并发性能。这件事在 4月4日当天就开始推进了。

**异步迁移过程**：策略是"标注废弃→渐进替换→全量切换"。先给需要迁移的同步方法打上 `@deprecated` 标记，保持向后兼容，然后实现 `diagnose_async()` 作为异步入口。迁移过程中有个细节：SSE StreamingResponse 的异步生成器（async generator）和同步代码混在一起时，容易触发 GeneratorExit 异常——这个问题在 V4 时没有充分暴露，到 V10 全量测试时才大规模复现。

**INT4 量化部署**：这是整个项目中最具挑战性的技术环节之一。RTX 3050 只有 4GB 显存，Qwen3-VL 的 FP16 版本需要 9.8GB，根本装不下。经过调研，确定了 INT4 量化的方案，理论显存占用约 2.6GB。但实际部署时遇到了一连串问题：

1. `bitsandbytes` 库在 Windows 环境下不支持，需要手动编译或改用替代加载方案；
2. 量化后模型的第一轮推理需要额外的预热时间（约 15-20 秒），因为需要做校准；
3. YOLOv8s 的 FP16 模型也在加载 GPU 显存，两个模型争抢同一块卡。

最终的解决方案是：YOLOv8s 使用 FP16 加载（约 50MB），Qwen3-VL 使用 INT4 量化加载（约 2.6GB），预留约 1GB 给推理缓冲。实际测试中显存占用约 3.7GB / 4GB，勉强够用但在并发场景下仍然紧张——这就是为什么后来设计了 90% 显存阈值的保护机制。

**其他改进**：类型注解实现了 12 模块 158 函数的 100% 覆盖，从代码质量的静态检查角度看是一次显著的提升。配置外部化减少了 9 处硬编码。测试基建方面，修复了 SQLAlchemy Index 的一个 tricky bug（索引名冲突导致建表失败），并建立了 1006 个测试基线。

项目评分从 89.8 提升到 **92.3**（+2.5）。

> **Git 记录**：V5 优化工作对应后续多个提交，包括配置外部化、类型注解补充等。此时的项目架构已经基本成型。

**遗留问题**：SSE StreamManager 存在 GeneratorExit 未处理的超时控制缺陷（V4 拆分时未覆盖的边缘情况）、推理时间未实际记录。这两个问题在 V10 的全量测试中被确认为 P1 级缺陷。

### 3.5 阶段五：V6-V9 质量加固与文档完善

#### 3.5.1 V6：测试补充和代码审计

4月4日到5日这段时间，核心代码已经稳定，开始补测试和质量审计。

V6 主要做了三件事：

1. **P0 紧急修复**：QwenModelLoader 的 `__new__()` API 兼容性问题。这个 bug 的根因是 HuggingFace Transformers 库的版本更新导致 API 签名变化，具体表现为模型加载时 `model_config` 参数不兼容。修复后补充了 8 个回归测试，确保同类问题能被自动捕获。

**V10 后端全量测试（2026-04-15）**

到了 4 月中旬，系统功能已经完备，代码质量也上去后，来了一次大规模的后端测试。这次测试规模相当可观：

- **BUG-003**：SSE 进度回调——主线程没有 event loop，无法接收异步进度更新。

这三个问题都被标记为 P1 级别（影响功能但不影响安全）。

#### 3.6.5 V29-V41：安全加固到最终交付

**安全是不可妥协的底线。**V29 开始，集中精力把系统安全全面加固。

加固的具体内容和对应版本（这些是 V41 CHANGELOG 中记录的累积安全特性）：

- **XSS 防护**：`html.escape` 转义 + `sanitize_response` 装饰器 + CSP 安全头。三个层面同时防护，确保即使用户输入恶意脚本也能被过滤
- **开放重定向防护**：登录重定向的 `redirect` 参数加入白名单校验，只允许跳转到本系统的合法页面
- **账户锁定机制**：连续 5 次登录失败后锁定账户 30 分钟，通过 Redis 计数器实现
- **SHA-256 令牌哈希**：不再是直接使用原始密码做哈希，而是在用户传入数据的基础上进行二次加密
- **Cookie 安全**：httpOnly + secure + samesite=lax 三重防护
- **错误信息脱敏**：生产模式下隐藏内部异常详情，防止敏感信息泄露
- **导航状态持久化**：localStorage + Pinia 双写策略解决页面切换后状态丢失的问题

**V38 修复导航状态持久化问题**的过程值得单独记录一下。在管理后台页面中，用户从一个标签页切换到另一个标签页再切回来时，之前的标签页状态会丢失。一开始以为是 Vue Router 的 keep-alive 配置问题，调试了半天才发现根本原因：Login.vue 的 `router.push('/')` 触发了根路径的重定向逻辑，导致整个导航栈被清空。修复方案是把 `router.push` 改成 `router.replace('/dashboard')`，直接跳到仪表盘页面不经过根路径——这样中间的重定向链路就断了。

**V40 最终验收**（已记录于 V41 CHANGELOG）：

- 后端 API 测试：46/46 PASS（100% 通过率）
- 前端 E2E 测试：14/14 PASS（100% 通过率）
- 总计：60/60 PASS（100% 通过率）

这与 V13 的 94.7% 相比是一个明显的进步——V13 失败的那个性能问题（诊断记录查询 6120ms）在 V40 中通过 eager loading 优化解决了。

## 八、总结

回顾 WheatAgent 从第一行代码到 V40 最终验收的整个过程，有几个体会值得记录：

**关于迭代节奏**：项目的开发节奏不是匀速的。初期（V1-V3）慢，因为需求和技术方案需要反复推敲；中期（V4-V9）快，因为方向明确后火力全开；后期（V10-V28）密，因为进入了"测-修-测-修"的缺陷修复循环。这种不均衡的节奏是真实开发的常态，而不是教科书里的理想曲线。

**关于"坏代码"的价值**：V3 的 God File（2202 行的 ai_diagnosis.py）现在回头看是一段糟糕的代码，但它在那时那刻是有存在价值的——它让团队快速验证了核心诊断链路是否可行。如果 V3 就追求架构完美，可能需要多花一倍的时间才能看到第一版诊断结果。关键是**在合适的时机重构**，而不是永远不重构或一开始就过度设计。

**关于量化和显存的矛盾**：RTX 3050 4GB 是项目的硬件天花板。INT4 量化在很大程度上缓解了问题，但没有根治——两个模型共占约 3.7GB，留给并发推理的余量非常有限。如果条件允许，升级到 8GB 甚至 12GB 显存的 GPU，可以显著提升并发能力。这是一个真实的工程约束——算法再好也要能为硬件做妥协。

**关于文档的重要性**：V8 的审计发现 58.6% 的文档与代码存在不一致，这个问题在单人或小团队开发中尤其常见——你心里知道代码怎么写的，就觉得不需要文档了。但两个月后回来看自己的代码，没有文档真的会忘。V7-V9 的文档建设虽然耗费了不少精力，但现在回想起来是值得的。

**关于测试的边际效益**：从 V5 的 1006 个测试到 V10 的 1102 个，再到最终 V40 的 60 项验收全通过，每一步都有边际收益递减的趋势——增加测试用例的速率在放缓，因为常规场景都已被覆盖。但这不意味着不该继续写测试——V10 暴露的 3 个 SSE GeneratorExit 问题恰恰说明，**罕见边界条件的测试需要更刻意地设计**，它们不会自动落到已有测试的覆盖范围内。

整个过程从 2026 年 2 月 11 日的第一次 `git commit`（`1bb77c60`）开始，到 2026 年 5 月 8 日的最后一次文档提交（`dce8d554`），跨越了 40 余个版本迭代，最终交付了一个端到端可用的、技术栈完整的、测试覆盖到位的小麦病害智能诊断系统。
